# SealMail Gateway 前端修订计划

## 1. 计划目标

本文档定义 SealMail Gateway 前端后续修订的阶段路线、交付边界和验收标准。

本计划的目标是：

- 统一后台管理页面的信息架构、页面骨架、筛选区、表格区和操作区。
- 强制全部页面采用 Ant Design 默认风格（AntDefault），不再建设独立视觉主题。
- 降低页面内联样式和重复状态逻辑，提升 React/TypeScript 代码可维护性。
- 修正固定侧边栏和内容区间距带来的响应式风险。
- 将复杂配置能力从过载弹窗中拆出，形成可持续演进的配置页面。
- 建立一致的表格、详情 Drawer、批量操作、错误反馈和权限不足体验。
- 在不扩大后端 API 变更范围的前提下，改善管理端安全和可用性。

## 2. 当前前端快照

当前前端具备以下基础：

- 前端位于 `sealmail-frontend`。
- 技术栈为 Vite、React、TypeScript、React Router 和 Ant Design。
- 路由集中在 `src/router/index.tsx`。
- 主布局集中在 `src/components/Layout/MainLayout.tsx`。
- 页面集中在 `src/pages`。
- API 调用集中在 `src/api/client.ts`。
- 权限判断集中在 `src/auth/permissions.ts`。
- 当前 `npm run lint` 与 `npm run build` 可通过。

当前主要前端债务：

- `MainLayout` 已经为内容区提供 padding，但多个页面内部继续重复 `padding: 24`，页面间距不一致。
- `src/index.css` 使用全局 Ant Design 选择器和 `!important` 固定侧边栏，移动端和窄屏布局风险较高。
- `CertificateAuthorities.tsx`、`DomainConfigs.tsx`、`Certificates.tsx` 等页面文件过大，表格列、表单、详情 Drawer 和业务动作混在同一文件。
- 域名配置页中的邮件认证能力承载在一个大型 Modal 中，DKIM、SPF、DMARC、DNS 记录和运行开关信息密度过高。
- 多个列表页重复实现筛选、分页、详情 Drawer、错误提示和操作按钮，交互细节不完全一致。
- `App.css` 仍保留 Vite 模板样式，当前未被实际入口引用，应清理或确认无残留依赖。
- 登录态使用 `localStorage` 存储 token 和用户信息，401 处理通过 `window.location.href` 强制刷新页面。
- 无权限访问时直接跳转到仪表盘，缺少明确的 403 反馈页。

## 3. 总体执行规则

所有阶段必须遵守以下规则：

- 每个阶段只处理一类前端变化，不混入后端业务重构。
- 页面结构修订不得改变现有 API 语义，除非阶段文档明确说明。
- 强制使用 Ant Design 默认风格（AntDefault）：不得新增自定义主题、品牌化渐变、大面积阴影、装饰性背景、复杂自绘视觉组件或覆盖 Ant Design 默认视觉语义。
- 优先复用 Ant Design 组件和现有业务类型，不引入新的 UI 框架。
- 所有业务页面必须统一使用 Ant Design 默认组件形态，包括 `Layout`、`Menu`、`Card`、`Table`、`Form`、`Modal`、`Drawer`、`Tabs`、`Alert`、`Result`、`Tag`、`Button`、`Space` 和 `Typography`。
- 先抽公共骨架和交互规范，再拆分具体业务页面。
- 表格、筛选、详情和批量操作必须保持可键盘访问和明确的加载状态。
- 危险操作必须保留确认提示，并统一确认文案、按钮语义和错误反馈。
- 不提交无关格式化、不重写未涉及页面、不移动后端文件。
- 每个阶段完成后至少执行 `npm run lint` 和 `npm run build`。

## 4. 修订原则

### 4.1 后台管理体验

SealMail Gateway 是安全网关管理端，界面应优先服务高频运维和审计工作：

- 信息密度应适中，便于扫描、筛选、比较和定位。
- 操作按钮应贴近对应业务对象，批量操作应有明确选择反馈。
- 状态标签、风险标签和危险动作应使用稳定一致的颜色语义。
- 避免营销式视觉表达，优先采用克制、清晰、可重复使用的管理端布局。

### 4.2 页面结构

目标页面结构：

```text
PageShell
  -> PageHeader
  -> optional Summary / Alert
  -> FilterBar
  -> DataTable
  -> DetailDrawer / FormModal
```

约束：

- 页面标题、描述、主操作按钮、次操作按钮应由统一 `PageHeader` 承载。
- 筛选控件统一放入 `FilterBar`，并支持重置、刷新和清晰的当前筛选状态。
- 表格分页、空状态、横向滚动、加载态和总数展示保持一致。
- 详情 Drawer 只用于查看或轻量操作，不承载大型配置流程。
- 大型配置流程应使用独立页面、Tabs 或分区表单。

### 4.3 样式边界

前端视觉风格强制采用 Ant Design 默认风格（AntDefault）。样式只允许服务布局、间距、响应式和必要的业务可读性，不允许重新定义一套视觉系统。

硬性约束：

- 禁止新增全局主题覆盖、暗色侧边栏以外的大面积自定义色块、渐变背景、玻璃拟态、复杂阴影和装饰性视觉元素。
- 禁止为普通业务页面自定义卡片阴影、圆角体系、按钮视觉体系、表格视觉体系或标签颜色体系。
- 禁止在页面级 CSS 中批量覆盖 `.ant-*` 默认样式来制造非 AntDefault 视觉。
- 允许使用 Ant Design token 做必要的布局和状态表达，但不得改变默认主题的整体观感。
- 允许为状态标签选择 Ant Design 预设颜色，但同一业务含义必须全站一致。

样式应优先收敛到组件 class 或页面局部 class：

- 避免在全局 CSS 中覆盖大量 `.ant-*` 选择器。
- 避免使用 `!important` 作为布局控制手段。
- 避免页面大量内联 `style={{ ... }}` 形成事实上的隐式设计系统。
- 对固定格式元素设置稳定宽度、最小宽度或横向滚动，防止内容挤压。
- 颜色、间距、圆角和阴影应优先使用 Ant Design 默认值；确需调整时必须通过少量局部布局样式表达。

## 5. 阶段计划

前端代码量较小，重构阶段按可验收边界粗分，不要求拆成过多小阶段。每个阶段可以作为一个主提交完成；如果单阶段风险偏大，可以按页面拆成多个小提交，但不得改变阶段验收目标。

## 阶段 1：AntDefault 基线与布局收敛

目标：先统一视觉和页面外壳，为后续页面重组提供稳定基线。

范围：

- 强制全站回到 Ant Design 默认风格（AntDefault），删除或停止扩散非必要自定义视觉。
- 确认 `src/App.css` 是否未被引用；若确实未使用，删除该模板遗留文件。
- 新增或抽取 `PageShell`、`PageHeader`、`FilterBar` 等基础组件。
- 将页面标题、描述和顶部操作按钮迁移到统一组件。
- 将全局固定侧边栏样式迁移到 `MainLayout` 的局部 class。
- 为窄屏场景提供可折叠或可替代的导航方案。
- 移除各页面重复的外层 `padding: 24`。

不包含：

- 不调整业务表单字段。
- 不改变 API 调用。
- 不深拆复杂业务页面。

验收：

- `npm run lint`
- `npm run build`
- 所有页面保持 AntDefault 观感，没有新增独立视觉主题。
- 桌面端展开/收起侧边栏后内容区间距正确。
- 窄屏下导航和内容不发生明显遮挡。

## 阶段 2：列表页与通用交互统一

目标：统一后台管理端最高频的列表、筛选、表格、详情和操作反馈。

范围：

- 统一分页参数、总数文案、快速跳页、每页条数选择。
- 统一空状态、加载状态、刷新按钮和错误提示。
- 统一列表页筛选条布局、重置行为和当前筛选反馈。
- 统一详情 Drawer 的宽度、标题、关闭行为和长文本展示。
- 为批量操作建立统一的选择反馈和操作条。
- 统一危险操作的确认弹窗文案、按钮语义和错误反馈。
- 将状态标签、算法标签、证书状态、隔离状态等展示组件抽成轻量公共组件。

重点页面：

- `ExceptionMails.tsx`
- `DlpQuarantine.tsx`
- `DlpPatterns.tsx`
- `DlpSelection.tsx`
- `AuditLogs.tsx`
- `Crl.tsx`

验收：

- `npm run lint`
- `npm run build`
- 主要列表页分页、筛选、刷新、空状态和详情 Drawer 表现一致。
- 批量操作在无选择、部分选择、不可操作选择时反馈清晰。
- 危险操作保留确认，成功和失败提示清晰。

## 阶段 3：复杂业务页面重组

目标：集中处理当前代码量最大、业务密度最高的页面，降低维护成本。

范围：

- 重组 `DomainConfigs.tsx`：将域名配置和邮件认证配置拆成更清晰的页面结构，DKIM、SPF、DMARC、DNS 记录和运行开关使用 Tabs 或独立分区承载。
- 重组 `CertificateAuthorities.tsx`：拆分 CA 表格列、筛选面板、Root CA 表单、Intermediate CA 表单、CSR 签发表单和详情 Drawer。
- 重组 `Certificates.tsx`：拆分终端证书表格列、导入表单、自签名表单、CA 签发表单、绑定操作和详情 Drawer。
- 视复杂度重组 `Settings.tsx`：将运行配置、Relay 策略、隔离策略、探测和测试邮件能力分区或拆组件。
- 将列表加载、刷新和动作提交逻辑抽到局部 hook，避免页面组件继续膨胀。

不包含：

- 不改变域名、证书、CA、系统设置等后端 API 语义。
- 不新增 DKIM/SPF/DMARC 后端能力。
- 不改变证书签发、吊销、信任、绑定的业务行为。

验收：

- `npm run lint`
- `npm run build`
- 域名增删改、邮件认证配置保存、DNS 记录生成与复制行为保持可用。
- CA 管理和终端证书管理的主要功能行为与拆分前一致。
- 大型页面文件显著缩小，表单、表格列和详情组件具备独立审查边界。

## 阶段 4：认证权限与最终验收

目标：补齐无权限、会话失效和全站回归验收，完成前端重构收口。

范围：

- 增加 403 页面或 Ant Design `Result` 状态页，替代无权限时静默跳转仪表盘。
- 将 401 处理从直接 `window.location.href` 收敛为统一认证状态处理。
- 评估 token 存储方式，明确 `localStorage` 的安全边界和后续迁移方案。
- 登录页保持 AntDefault 风格，增加更明确的失败反馈和提交加载状态。
- 用户菜单可展示角色、邮箱或当前权限摘要。
- 对全部页面做一次 AntDefault、响应式、表格、弹窗、Drawer、错误反馈和权限路径回归。

不包含：

- 不在本阶段强制迁移为 HttpOnly Cookie，除非后端同时提供完整支持。
- 不改变现有角色模型。

验收：

- `npm run lint`
- `npm run build`
- 无权限访问能看到明确反馈。
- 会话失效后能稳定回到登录页，不出现重复弹错或刷新循环。
- 全部页面符合 AntDefault 约束，未残留明显自定义视觉体系。

## 6. 建议落地顺序

建议按以下顺序执行：

1. 阶段 1：AntDefault 基线与布局收敛。
2. 阶段 2：列表页与通用交互统一。
3. 阶段 3：复杂业务页面重组。
4. 阶段 4：认证权限与最终验收。

其中阶段 1 是所有后续重构的硬前置；阶段 2 和阶段 3 可以按页面拆提交，但验收应按阶段整体完成。

## 7. 验收命令

每个阶段至少执行：

```bash
cd sealmail-frontend
npm run lint
npm run build
```

涉及响应式布局的阶段，还应人工检查：

- 桌面端侧边栏展开。
- 桌面端侧边栏收起。
- 窄屏或移动宽度下导航、表格和弹窗显示。
- 表格横向滚动、长文本、省略号和详情 Drawer 展示。

涉及表单和危险操作的阶段，还应人工检查：

- 创建、编辑、删除、吊销、信任、放行、拒绝等操作。
- 成功提示、失败提示、加载态和取消操作。
- 无权限访问和会话失效路径。

## 8. 非目标

以下内容不属于本前端修订计划的直接目标：

- 后端模块边界重构。
- 邮件处理管道迁移。
- 数据库 migration 设计。
- 新增 DKIM/SPF/DMARC 后端能力。
- 新增证书算法能力。
- 引入新的前端 UI 框架或状态管理框架。

如上述事项需要调整，应在对应后端或跨端计划中单独定义阶段、验收和回滚策略。
